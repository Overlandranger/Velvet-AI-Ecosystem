Core Doctrine

LLMs propose.

Gates authorize.

Executors act.

Receipts prove.

No direct prompt-to-hardware path. No social channel grants authority. No token grants runtime control.

Drive OS

Vehicle and mobility surfaces. The first body of Velvet begins with retrofit vehicle intelligence, CAN-aware adapters, local control paths, and receipt-backed authority.

Forge OS

Fabrication surfaces such as 3D printers, CNC, and maker systems. The same doctrine applies: local control, bounded adapters, and receipts.

Castle / Move / Industries

Future home, portable, and industrial surfaces. Each surface gets its own adapter pattern without becoming Velvet’s authority source.

DriveFi and VELV

DriveFi is Velvet’s experimental economic layer for receipt-backed machine work, motion, presence, and local value generation.

VELV is not required to use, study, build, or contribute to Velvet’s core architecture.

Token ownership does not grant runtime authority, governance control, hardware access, executor privileges, or system permissions.

The token layer must never bypass Velvet’s authority gates.

Boundary Statement

Velvet’s public repos and docs are early architectural baselines. Some modules are scaffolds, some are active implementation layers, and some are doctrine-first boundaries.

Repo boundaries are not cosmetic. They prevent authority leakage.

No single repo, social channel, token layer, or hosted AI collaborator should quietly become the whole machine.
